# Wisp releases

Stable and Nightly are channels of the same product. The installer, GitHub release,
updater and website use the same Markdown notes. The website reads published GitHub
Releases, so drafts never appear in the public changelog.

## Stable

1. Add user-facing notes to `releases/next.md` while changes are developed. Use a
   `# Title`, then `## New`, `## Improved`, or `## Fixed` and bullet points. Explain
   benefits and any action users need to take. Leave test coverage, CI changes and
   implementation details out of public notes. Images use absolute HTTPS URLs.
2. Commit all work, update your local `main`, then run `pnpm release patch` or
   `pnpm release minor`. An explicit version also works: `pnpm release 0.1.0`.
   `pnpm release:dry patch` previews the commands without changing files or pushing.
3. release-it checks the branch and clean working tree, runs checks and tests,
   archives the notes in `releases/<version>.md`, resets `next.md`, synchronizes
   workspace/Tauri/Cargo versions and lockfiles, and pushes a release commit and tag.
   Use a stable X.Y.Z version; prereleases are generated by CI instead.
4. Actions builds, signs and verifies the installer, then creates a draft containing
   those exact notes and `latest.json`. Review it, publish it and mark it latest.
   If notes need a correction, update the source and rerun the tagged build while
   it is still a draft, so the release body and updater manifest stay identical.

Squash merges are supported: stable notes and version increments do not depend on
individual commit history or Conventional Commits. Keep a useful PR title because
the squash commit message appears in automatic Nightly notes.

Do not publish from a checkout containing unfinished work. A failed preparation
may leave local version/notes changes to inspect before retrying. Release tooling
does not publish npm packages or automatically publish stable drafts.

## Nightly

Every push to `main` runs the release pipeline. After checks pass, CI assigns
`<current stable, next patch>-nightly.<run number>.<attempt>` only in the build
checkout. No version commits are pushed back to `main`. Each installer has an
immutable version tag targeting the exact source SHA. Notes summarize squash/merge
commits since the latest stable tag and link to the source commit.

The signed installer must pass installation/upgrade tests before the prerelease
is published. The moving `nightly` prerelease holds only the latest updater
manifest; it is updated last and is excluded from the web history. Failed builds
leave the previous feed intact. Re-running a workflow generates a distinct build.

## Updates and changelog

- Stable feed: GitHub `releases/latest/download/latest.json` (kept compatible with
  existing installs).
- Nightly feed: GitHub `releases/download/nightly/latest.json`. Manifest URLs point
  to immutable versioned artifacts, never a moving installer.
- Packaging stamps the release version into the staged addon TOC. Generated
  transport helpers inherit that version when installed. `/wisp diag` reports
  the loaded addon and desktop/bridge versions and flags mismatches; reload WoW
  after updating the addon. Source TOCs are labeled `development`.
- App Settings → App updates persists the selected channel. Fresh Nightly installs
  default to Nightly; stable installs default to Stable. Switching clears pending
  updates. Returning from Nightly explicitly permits an older stable version;
  ordinary updates only move forward within the selected channel. Both channels
  share the installation and user data; they are not side-by-side apps.
- `/changelog` shows stable releases; `?channel=nightly` shows previews.
  `/changelog/<version>` is a permanent link. The website and app use the same
  restricted Markdown renderer (headings, lists, links, images, code; raw HTML is
  escaped). Release notes currently remain in their authored language.
- To correct published notes, edit the GitHub release body and synchronize the
  notes field in its updater manifest. Preserve every other manifest field,
  including installer URLs and signatures, so the website and app agree.
- The web uses the public GitHub Releases API, cached for five minutes, with
  ten releases per page within each channel and separate failure states.
  Optionally set `GITHUB_RELEASES_TOKEN` on the web
  server for a higher API quota. It is never sent to the browser.

Both channels require the existing `TAURI_SIGNING_PRIVATE_KEY` Actions secret
(and its password secret if configured). Never replace the checked-in public key
to add a channel. GitHub Actions must have permission to create releases/tags.
